# Design Spec

## Current-State Read

`repository_prisma` publishes two externalized runtime bundles from `src/index.ts`: `package.json.exports.import` selects `dist/index.mjs`, and `exports.require` selects `dist/index.js`. The ESM bundle currently retains named runtime imports from `@prisma/client` in the root-client lifecycle owner and the `Models` runtime-value module. `@prisma/client` is a CommonJS-generated peer. Node/Vitest may synthesize named exports from some generated shapes, but that is not a reliable ESM contract; the synthetic-peer probe fails the current ESM bundle before package initialization. The CJS bundle already uses `require` and remains the preserved path. Evidence is in `investigation-notes.md` and `interop-probe-results.md`; behavior authority is in `requirements.md`.

The relevant owners remain healthy: `PrismaClientLifecycle` owns raw root-client construction/readiness; `models.ts` owns the public runtime model-name value; `src/index.ts` is only a public export barrel; tsup owns format emission. The defect is a narrow external peer boundary mistake, not a transaction, repository, lifecycle, schema, or data-ownership problem. The target must preserve all public exports and Prisma operations, keep `@prisma/client` external, and avoid adding a generic compatibility layer or peer version policy.

## Intended Change

1. In the two source modules that need Prisma runtime values, replace named runtime imports with a default import of the CommonJS namespace and destructure only the required property:
   - `src/lib/client/lifecycle.ts`: `PrismaClient` for raw root-client construction.
   - `src/lib/models.ts`: `Prisma` for `Prisma.ModelName`.
2. Convert every package-source Prisma reference that is type-only to explicit `import type` so it cannot create an external runtime import: `base-repository.ts`, `context.ts`, `prisma-manager.ts`, `repository-factory.ts`, and `types-experiment.ts`. Preserve existing type contracts.
3. Update runtime test imports that use Prisma values to the same safe default-import pattern; remove the unused runtime import in `integration.test.ts`.
4. Add a focused package regression script that loads the built package's ESM entry under a synthetic CommonJS peer whose exports are dynamically assigned and therefore do not provide detectable ESM named exports. Keep the existing installed package smoke for generated-peer CJS/ESM/declaration behavior.
5. Update package/release documentation and version metadata for `1.0.10`; do not change the peer range, public export list, Prisma schema, migrations, or persisted data.

The implementation must keep runtime values and TypeScript namespaces as separate
bindings. A destructured runtime value cannot serve as a TypeScript namespace, so
mixed value/type consumers must alias both imports explicitly:

```ts
// src/lib/client/lifecycle.ts — runtime value plus type alias
import PrismaClientPackage from '@prisma/client';
import type { PrismaClient as PrismaClientType } from '@prisma/client';

const { PrismaClient: PrismaClientRuntime } = PrismaClientPackage;

const defaultClientFactory = (): PrismaClientType =>
  new PrismaClientRuntime();

// src/lib/models.ts — runtime value plus Prisma type namespace
import PrismaClientPackage from '@prisma/client';
import type { Prisma as PrismaTypes } from '@prisma/client';

const { Prisma: PrismaRuntime } = PrismaClientPackage;
export const Models = PrismaRuntime.ModelName;
export type ModelName = PrismaTypes.ModelName;

// src/tests/transaction-context.test.ts — runtime enum plus transaction type
import PrismaClientPackage from '@prisma/client';
import type { Prisma as PrismaTypes } from '@prisma/client';

const { Prisma: PrismaRuntime } = PrismaClientPackage;
const isolationLevel = PrismaRuntime.TransactionIsolationLevel.Serializable;
const transactionClient = {} as PrismaTypes.TransactionClient;
```

For runtime-only consumers such as `src/tests/public-initialization.test.ts`, use
only the runtime alias:

```ts
import PrismaClientPackage from '@prisma/client';
const { PrismaClient: PrismaClientRuntime } = PrismaClientPackage;
const client = new PrismaClientRuntime({ datasourceUrl });
```

For type-only consumers, use only an explicit type import, for example
`import type { Prisma, PrismaClient } from '@prisma/client';`. The CJS bundle may
use its normal `require` interop generated by tsup. No named runtime import from
`@prisma/client` may remain in emitted ESM.

## Terminology

- `CommonJS namespace`: The default value returned when an ESM default import consumes the external `@prisma/client` CommonJS module; it is destructured for required runtime properties.
- `Runtime Prisma value`: A property needed at execution time (`Prisma` or `PrismaClient`), distinguished from TypeScript-only Prisma types.

## Ownership Boundaries

The package export condition is the authoritative consumer boundary for format selection. The external peer's default namespace is the authoritative runtime-value boundary for `Prisma` and `PrismaClient`; package code may destructure required properties but may not infer or synthesize named exports. `PrismaClientLifecycle` remains the sole owner of raw client construction. `models.ts` remains the sole owner of the public `Models` runtime value. All other package modules depend on typed contracts or existing owners and do not bypass them.

## Dependency Rules

- `lifecycle.ts` may depend on the external peer's default namespace for constructing `PrismaClient`; it may not use a named runtime import or expose the namespace as a new public API. Its annotations use a separate `import type { PrismaClient as PrismaClientType }` binding.
- `models.ts` may depend on the external peer's default namespace for `Prisma.ModelName`; it may not construct clients or own lifecycle state. Its runtime `PrismaRuntime` and type-only `PrismaTypes` bindings remain separate.
- Type-only source files depend on `@prisma/client` through `import type` only.
- `src/index.ts` depends on module owners for exports and contains no interop logic.
- tsup keeps `@prisma/client` external; package code must not bundle a generated client or add a peer fallback.
- Tests may install or synthesize a peer only in the harness; production source must not detect, patch, or branch on peer module shape.
- Forbidden: named runtime peer imports in ESM output, dynamic import fallback, `createRequire` compatibility wrappers, alternate package entrypoints, peer-range changes, raw-client duplication, or unrelated repository/lifecycle changes.

| Topic | Good Example | Bad / Avoided Shape | Why The Example Matters |
| --- | --- | --- | --- |

## Key Tradeoffs

- Direct default imports are minimally invasive and preserve existing owners, but each runtime owner expresses its own dependency rather than introducing a shared adapter. This is intentional to keep concerns semantically tight.
- A synthetic peer probe adds a small test harness and temporary loader complexity, but it is necessary because the locally generated peer's static names produce a false-green baseline.
- Version `1.0.10` is a patch release even though no public function signature changes; it corrects a published package compatibility defect. Publication remains separate from source readiness.

## Risks

- If a consumer's peer omits the expected runtime properties entirely, default destructuring cannot make the peer valid; this is outside the declared peer contract and is intentionally not polyfilled.
- The exact reported Linux ARM64/Vitest workspace was unavailable locally. The regression covers the platform-independent CJS named-export assumption; final downstream validation should still run in the consumer workspace.
- Registry publication may require user-authorized tag/publish action; no publication claim is made from local build evidence.

## Guidance For Implementation

- Keep the source changes narrow and inspect both generated bundles after every import change.
- Use the exact default namespace pattern, with a descriptive local alias such as `PrismaClientPackage`; pair it with a separate aliased type-only import whenever the module also needs a Prisma type namespace. Use `PrismaClientRuntime`/`PrismaClientType` in lifecycle, `PrismaRuntime`/`PrismaTypes` in models, and `PrismaRuntime`/`PrismaTypes` in `transaction-context.test.ts`. Do not use `createRequire`, dynamic import, `module.exports` shims, or runtime feature detection.
- Preserve `PrismaClientLifecycle` construction and all existing option/logging/readiness behavior.
- Preserve `Models` identity and public exports.
- Ensure test-only runtime Prisma values use the same safe pattern or are removed if unused.
- Ensure the new probe fails against the baseline named-import artifact and passes against the corrected artifact.
